## The tooling detour — an honest post-mortem of my own optimization work

I spent hours hardening `capture.mjs` and I want the record to be accurate about what that bought.

**What it genuinely bought (verified, not claimed):** six silent-failure modes closed. The harness
went from exiting 0 with 14 of 24 shots dead, to failing loud. It now waits for the canvas (it never
did — a `sleep` hid that for the whole project), records the URL that produced each artifact, detects
a blank frame, and refuses to let a partial evidence set reach a judge. Plus `preflight.mjs`, which
proves the evidence chain works — including that the query params actually take effect — before an
attempt is spent. **That is real and it is done.**

**What it did NOT buy: speed.** Three swings, three misses, all measured:
1. `--jobs 5` batching: **12:59** and 10 dead shots (vs ~10 min serial). Concurrency on a CPU-bound
   rasterizer is contention, not throughput.
2. Full-frame settle sampling: **31:15**. I took eight 6.2 MP screenshots per shot to decide when to
   take one more. The readiness check became the cost it was meant to save.
3. Clip-based settle: aborted mid-run. Looked slow — and here is the worst part:

**I cannot make ANY clean speed claim, because I never controlled for machine load.** The ~10 min
serial baseline was measured on an idle box. Every "optimized" run was measured while writer agents,
judges and auditors were hammering the same CPU. I was comparing numbers that were never comparable,
and I nearly logged a fourth false conclusion (I hypothesized the animated scene "never settles" —
then checked, and `never-settled: 0` proved me wrong before I acted on it).

**The lesson, and it is about me, not the tool:** measuring is not enough. An unqualified measurement
under an uncontrolled variable is just a slower way to be confidently wrong. STOP optimizing when the
thing is correct; optimize later, cold, with the machine quiet — and only when a real cost number
says it matters.

## Anti-patterns observed (mine, this run)

- **Capturing before the code is closed.** Evidence born dead. Cost it twice: S3 landed mid-way
  through the lighting capture set (forcing a full recapture), and I nearly captured 27 interaction
  shots while an alarm-copy fix was in flight that changes the text visible in 10 of them. The order
  is not negotiable: **code closed → preflight → capture → judge.** Never overlapped.

## Anti-patterns observed

- **Polishing the symptom.** Three lineages of SURFACE tuned annotation geometry while the annotated
  device had no pixels. The blind judge kept saying "bare junction stubs" and it was taken as a
  styling note, not a literal report. **Read the judge's defects as literal pixel facts, not opinions.**
- **Trusting a green suite as evidence of correctness.** It is evidence of *no regression*, nothing more.
- **Declaring a change done without independent verification.** Caught twice on the kit deltas themselves.
- **Ignoring the writer's own risk flag.** The lighting a1 writer wrote its biggest risk in plain text
  in its handoff. It went to the judge unlooked-at and came back a failure.

## Appended live — 2026-07-14 (late night), L3 evidence-chain incident (retro-vivo; STAGED)

**The orchestrator's own shell chain swallowed a preflight FAIL.** `preflight ... 2>&1 | tail -4 &&
capture ...` — the `&&` gates on TAIL's exit code, not preflight's, so a FAILED preflight (its
verdict line literally says "Do NOT spend a gate attempt on this evidence chain") flowed straight
into a 46-minute capture of dead evidence; the same `tail` also truncated WHICH two problems
failed. Caught only because a status check happened to read the output file's last lines. 14 dead

command may never sit behind a pipe inside a && chain**; capture its exit explicitly (`set -o
pipefail`, or run the gate standalone and test `$?`), and NEVER truncate a gate tool's output —
full log to a file, tail the FILE for display. Same family as delta #16 (an instrument's verdict
must not be silently laundered by its harness).
