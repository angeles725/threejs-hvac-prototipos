# VISOR — distribution & access runbook

How the `visor-angeles` viewer is published, gated, and extended. Read this before adding a project
or touching access keys.

- **Cloudflare Pages project:** `visor-angeles`
- **Live domains:** `visor-angeles.pages.dev` and the custom domain **`visor.angeles-group.org`**
  (already attached to the project)
- **Deploy source:** `disenos/cinemex-hvac-lorawan/publish/` (gitignored — it is generated)
- **Production branch:** `main`

## Layout of `publish/`

```
publish/
  index.html          ← the PORTAL (hand-staged; copied from portal/index.html)
  protection.js       ← portal shell guard (obfuscated, fixed name)
  _headers            ← Cloudflare cache policy (generated by the cinemex build)
  assets/             ← portal thumbnails
  p/
    cinemex/          ← one dir per project, each its own build-publish output
    dhl/
    hotspot/
```

Each project is served at `https://visor.angeles-group.org/p/<id>/`. **These are the direct links you
send clients.** Pages 308-redirects `/p/<id>/index.html` → the clean `/p/<id>/` URL.

## Distribution: portal vs direct link

- The **portal** (`/`) is an open gallery. Its cards are real `<a href="p/<id>/">` links that
  **navigate** to the project (the address bar shows the full URL). It does NOT use an iframe.
- The portal is **not** gated — it only lists projects. The gate lives on each project.
- To add/remove a project card, edit the `PROYECTOS` array in `portal/index.html`, then re-stage
  (`cp portal/index.html publish/index.html`). Keep `portal/index.html` as the source of truth —
  it drifted stale once; do not edit `publish/index.html` directly.

## Access gate — passwords

**Friction, not security.** The gated page still ships to the browser; the gate hides it behind a
passcode overlay and holds the 3D until unlock. It keeps honest people out of a client demo — it is
NOT access control. Real options, if ever needed: Cloudflare Access (per-identity) or payload
encryption. See the header of `gate.mjs` for the full threat model.

How it works:

- **One key per project.** `keygen.mjs` generates keys shaped `PROJECT-XXXX-XXXX`.
- Only `SHA-256(key + salt)` ships (in `gate-keys.json`, safe to publish). The cleartext keys live in
  **`gate-secret.txt`** — gitignored, never committed. Share those with the client.
- At build time each project's `build-publish.mjs` calls `injectGate(...)` (from its local `gate.mjs`),
  which injects a `<head>` overlay AND rewrites the heavy `<script type="module">` into an inert
  `application/ag-deferred` tag. The 3D module only boots after a correct key — so the login sits on
  an empty page, no jank.
- On success the browser stores `localStorage['agkey:<id>'] = <hash>`. Because the token IS the hash,
  rotating a key (new hash) auto-invalidates every stored unlock — no per-visitor cleanup.

### Rotate the keys

```bash
node disenos/cinemex-hvac-lorawan/keygen.mjs   # regenerates ALL keys + salts + hashes
# rebuild the 3 projects, then redeploy (see below)
```

> ⚠️ `keygen.mjs` regenerates **every** key on each run, so rotating one reissues all of them —
> redistribute the new keys to every client. (If you ever need additive/independent rotation, teach
> keygen to preserve existing entries.)

## Deploy

```bash
cd disenos/cinemex-hvac-lorawan
node build-publish.mjs                 # cinemex → publish/p/cinemex + _headers + portal guard
node ../datacenter-dhl/build-publish.mjs
node ../datacenter-hotspot/build-publish.mjs
cp portal/index.html publish/index.html   # only if the portal changed
npx wrangler pages deploy publish --project-name=visor-angeles --branch=main --commit-dirty=true
```

Verify live with `curl -sSL` (NOT plain curl — `.html` paths 308-redirect and return empty without
`-L`). Grep the served HTML for `AG_GATE_V2` (gate present) and `application/ag-deferred` (3D deferred).

### Deploy gotchas

- **Auth:** wrangler authenticates from the ambient environment. The repo-root `.cf-token` is
  currently **invalid** (API error 9109) — it works for nothing; do not rely on it for Cloudflare API
  calls (e.g. cache purge). Get a fresh token if you need the API directly.
- **Propagation:** after a deploy, directory-index URLs (`/p/<id>/`) can lag seconds–1 min across
  Cloudflare edges. A `?cachebuster=` query does NOT help (Pages keys static assets by path, ignoring
  the query). Just wait and re-check with `curl -sSL`.
- `cf-cache-status: DYNAMIC` on HTML = served fresh from origin (HTML is not edge-cached here).

## Add a new project to the visor

1. Give the project a `build-publish.mjs` that emits to `../cinemex-hvac-lorawan/publish/p/<id>/`
   (mirror `datacenter-hotspot/build-publish.mjs` — closest template: two standalone pages, inline
   modules, static three imports).
2. Copy `gate.mjs` and `publish-hash.mjs` into the new project dir (SHARED-BY-COPY — byte-identical,
   kept in sync by hand; build scripts never import across project roots).
3. In the new `build-publish.mjs`: `import { injectGate, loadGateConfig } from './gate.mjs'`, load the
   config with `loadGateConfig(join(CINEMEX, 'gate-keys.json'), '<id>')`, and wrap each shipped page's
   HTML with `injectGate(...)` (outermost, after `rewriteRefs`).
4. Add `{ id: '<id>', title: '…' }` to the `PROJECTS` array in `keygen.mjs`, then run keygen (this
   reissues ALL keys — see the warning above).
5. Add the project's hashed-bundle patterns to the `HEADERS` block in
   `cinemex-hvac-lorawan/build-publish.mjs` (it owns `publish/_headers`) so they cache immutably.
6. Add a card to `PROYECTOS` in `portal/index.html` + a thumbnail in `publish/assets/`.
7. Build all + deploy (above).
