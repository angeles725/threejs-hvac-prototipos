## Mechanisms worth adopting

### 1. Locked-sequential pass pipeline with machine-checkable unlock

- **How it works exactly** [CERT-web]: 8 ordered passes hardcoded in `sculpt_pass_orchestrator.py`: `blockout → structural-pass → form-refinement → material-pass → surface-pass → lighting-pass → interaction-pass → optimization-pass`. The state lives *inside the spec JSON* under `sculptPipeline`: `{passGateMode: "locked-sequential", passOrder, currentPass, completedPasses, lastCompletedPass, blockedReason, nextRequiredEvidence[]}`. The state is never edited by hand: `sync` **derives** `completedPasses` from `reviewHistory` — a pass counts as completed only if some review entry has `passId == pass && action == "continue"` AND (for visual passes) has `visualEvidence.renderScreenshot` + `visualEvidence.comparisonImage` + numeric `aiVisionScore >= visualAcceptanceThreshold` (default 0.7) + zero feature-gate failures. Completion scanning stops at the first incomplete pass (no skipping). `check --pass-id X` exits 1 if X is not the current unlocked pass, printing "complete '<previous>' with reviewHistory.action=continue and screenshot evidence first". The code generator (`generate_threejs_factory.py`) refuses future `--pass-id`s.
- **Dual-track mapping**: put an identical `pipeline:` block in `design-spec.yaml` (per track: `voxel` passes and `realistic`/Blender-MCP passes). A small `gate.py` (or the skill's own checklist discipline) derives `currentPass` from `review_history` entries instead of trusting the agent's memory. Both tracks share the rule: the review record is the *only* thing that advances state, so a compaction or session restart re-derives progress from the YAML.

### 2. Evidence-gated `continue` — the reviewer cannot pass a pass without artifacts

- **How it works exactly** [CERT-web]: `append_sculpt_review.py` hard-fails (raises) when a visual pass uses `--action continue` without: `--render-screenshot`, `--comparison-image`, `--ai-vision-score`, score >= threshold, and (if `layerScoresRequired`) `--layer-scores-json` covering every layer in `requiredLayerScores`. The recorded JSON entry shape: `{timestamp, passId, estimatedFidelity, aiVisionScore, visualAcceptanceThreshold, layerScores{}, featureReviews[], action, summary, matched[], mismatches[], specFixes[], codeFixes[], evidence[], visualEvidence{referenceScreenshot, renderScreenshot, comparisonImage, cameraView, notes, aiVisionNotes}}`. The same entry is mirrored into a flat `visualEvidence[]` history array.
- **Dual-track mapping**: our env can't screenshot WebGL headlessly (known limitation), so the Three.js voxel track substitutes "user-supplied screenshot path" (the plugin already supports `fallbackCapture: "user-supplied-screenshot-path"`); the Blender-MCP track can render actual viewport/Cycles screenshots via MCP — evidence gating is *fully automatable* there. Record each gate review as a YAML entry with the same fields; refuse to mark a gate passed in design-spec.yaml without a screenshot path + score.

### 3. Five fixed layer scores + review actions vocabulary

- **How it works exactly** [CERT-web]: every AI-vision review scores 0–1 on exactly five layers: `silhouetteProportion`, `componentStructure`, `formDetail`, `materialSurface`, `lightingCamera` (definitions in `references/browser-screenshot-feedback.md`, "AI Vision Scorecard"). Rule: "Do not hide a critical failed layer inside a high average." The decision is one of five actions: `continue | refine-spec | refine-code | request-input | stop`, with a root-cause taxonomy (`spec gap | code gap | rendering/lighting gap | reference ambiguity | performance tradeoff`). Hard rule: `refine-spec` → fix the spec first and re-validate, "Do not patch code around a bad spec."
- **Dual-track mapping**: adopt verbatim as the gate-review rubric in design-spec.yaml. The `refine-spec` vs `refine-code` split is the single most valuable discipline: it prevents the loop where the agent hacks HTML/Blender code to compensate for a wrong spec. `request-input` maps to "ask the client/user for a reference photo or dimension".

### 4. Feature-level review gate (semantic subsystems, not meshes)

- **How it works exactly** [CERT-web]: `visual_feature_gate.py` — spec declares `featureReviewTargets[]`: `{id, name, tier: critical|important|detail, passIds[], minimumScore, mustPass, componentRefs[], evidenceRefs[]}`. Policy (in `selfCorrectLoop.visualAcceptance.featureReviewPolicy`): max **5 critical** and **3 important** targets per pass; every critical must be reviewed, visible, and score >= its `minimumScore` (default 0.8) *independently* — "A failed critical feature fails the pass even when the global score is high." Important features only need a reviewed **average** >= 0.65. Repeated parts are grouped into one semantic system ("review three cabins as `cabin-system`, not three separate cabin targets"). Starter targets are placeholders that must be replaced with object-specific systems.
- **Dual-track mapping**: for a datacenter/HVAC scene: critical targets like `crac-unit-system`, `rack-rows`, `raised-floor-grid`, `cable-tray-system`, `hot-aisle-containment` — each with its own threshold in design-spec.yaml. Prevents "global score 0.8 but the chillers are missing" acceptance.

### 5. Pre-spec assessment gate + quality contract (anti-shallow-spec)

- **How it works exactly** [CERT-web]: before the spec exists, score 8 complexity axes 0–3 (`silhouetteComplexity, componentCount, hierarchyDepth, repetitionDensity, materialLayerCount, localDetailDensity, occlusionRisk, actionReadinessNeed`) → tier `simple|moderate|complex|ultra-complex` → write a `qualityContract`: `{definitionOfDone[], minimumSpecDepth{macroComponents, mesoComponents, microFeatureGroups, materialLayers, repetitionSystems, reviewViewpoints}, featureGroups[{id, qualityCriteria, evidenceRefs, failureModes}], visualDeltaChecks[], antiShallowSpecRules[]}`. Example anti-shallow rules (verbatim from `new_sculpt_spec.py`): "Do not proceed to code if the spec only contains a root component for a moderate or complex object"; "Do not pass material look-dev when albedo is reused as roughness, height, normal, or AO." Litmus test (`pre-spec-assessment.md`): "The gate should block code generation when the spec could describe many different objects instead of the provided reference." Weak-vs-strong feature-group examples given ("make leaves look good" vs a full canopy-mass description).
- **Dual-track mapping**: run this assessment before writing design-spec.yaml. `minimumSpecDepth` maps directly: a hotel-tower voxel scene rated `complex` must declare N meso components and repetition systems (windows, balconies, HVAC units) before any HTML is generated. `validate_sculpt_spec.py --strict-quality` is the model for a `spec lint` step.

### 6. ObjectSculptSpec v2 schema — component/material/action fields

- **How it works exactly** [CERT-web]: full template in `new_sculpt_spec.py` (preserved). Key structures beyond the obvious:
  - Component: `{id, level: macro|meso|micro, role, importance, confidence, primitive, geometryDescriptor{topologyIntent, edgeTreatment{bevelRadius}, deformationStack, uvStrategy, normalStrategy}, parent, attachment, dimensions{+confidence}, transform, actionProfile, material, materialLayers[], localFeatures[], surfaceDetail{macroRoughness, microRoughness, bumpAmplitude, normalPattern, displacementPattern, occlusionPattern, edgeWearPattern}, evidenceRefs[], fidelityTier}`.
  - `actionProfile`: `{animationRole: root|static|articulated|deformable|detachable|breakable|effect-emitter|socket-only, pivot{mode, localPosition, axis, confidence}, transformChannels{translate…materialState}, sockets[], collider{type, offset, scale, isTrigger}, constraints[], destruction{breakable, fractureGroup, seamRefs, detachableFragments, breakImpulse, debrisMaterial}}`.
  - Material: `{albedo{dominant, secondary[], samplingNotes}, colorVariation{palette, pattern, amplitude, heightCorrelation}, textureResolution, textureProjection{mode, repeat, texelDensityIntent}, surfaceFrequencyBands[{id: macro|meso|micro, frequency, amplitude, role}], roughness{base, variation, map, localResponse}, metalness, normal, bump, displacement{silhouetteAffects}, ambientOcclusion{cavityStrength, contactShadowBias}, wear{edgeWear, scratches, chips}, dirt{amount, cavityBias, color}, localOverrides[], shaderNotes[]}`.
  - `viewEvidence[]`: normalized image regions `{x,y,width,height}` + observations + confidence — every component/feature must cite an `evidenceRef`.
  - Runtime contract: each movable part = `THREE.Group` pivot with mesh child; `root.userData.sculptRuntime = {nodes, meshes, sockets, colliders, destructionGroups}`.
- **Dual-track mapping**: design-spec.yaml adopts `level/importance/confidence/evidenceRefs` per component, `surfaceFrequencyBands` for realistic-track materials, and `actionProfile` (pivot+sockets) for anything that later animates (doors, fans, dampers). In Blender-MCP the pivot rule becomes "set object origin at the semantic joint"; in Three.js it stays a Group wrapper. Confidence-per-dimension is what lets a later pass legitimately revise sizes.

### 7. Attachment contract — no floating child parts

- **How it works exactly** [CERT-web]: any child appendage (role/name/primitive matching a token set: branch, limb, handle, tube, cable, pipe, hinge, socket… or primitive in {cylinder, cone, capsule, tube, curve-sweep}) must define `attachment{parentSocket, localStart[3], localEnd[3], contactType: embedded|socket|overlap|hinge|surface-contact|glued, embedDepth or overlap > 0, gapTolerance}`. The orchestrator blocks `structural-pass`/`form-refinement` while any such component is incomplete. Generator rule: "place the pivot group at `localStart`, generate the visible mesh from `localStart` to `localEnd`... Do not center the mesh at an arbitrary transform position."
- **Dual-track mapping**: directly fixes the most common voxel-scene defect: pipes/ducts/conduits floating off walls. In design-spec.yaml, ducts, cable trays, pipe runs get `local_start/local_end/embed_depth`; the Three.js factory builds tubes endpoint-to-endpoint; Blender-MCP uses the same endpoints for curve objects.

### 8. Reference-PBR extraction as an *inference gate with confidence*

- **How it works exactly** [CERT-web]: `extract_reference_pbr.py` (pure stdlib, own PNG codec):
  1. Foreground mask: corner-sample background median + noise; pixel is foreground if color distance > max(24, 2.4×noise) or (saturation>0.16 and luma<0.94); alpha mask if >3% transparent pixels.
  2. Palette: mini k-means (k≤6, 8 iterations) over ≤7000 masked samples, ordered by cluster population.
  3. De-lit albedo: divide by blurred low-frequency luma — `scale = clamp((medianLuma/localShade)^0.42, 0.72, 1.35)`.
  4. Height: high-pass of luma (luma − blur) normalized by p05–p95 value range; normal: Sobel-like gradient of height, strength auto-tuned `clamp(10 + p90gradient×75, 10, 38)`; AO: `1 − cavity×8` where cavity = mean(4-neighbors) − height; roughness heuristic: `0.68 + min(0.22, gradient×2.6) + (0.5−height)×0.12 − brightHighlight×0.22` (cavities rougher, highlights smoother).
  5. **Confidence** = `0.44 + resolution×0.14 + maskQuality×0.14 + dynamicRange×0.12 + detail×0.16 − warningPenalty`, **hard-capped at 0.86 for a single image** (0.93 multi-view). Verdict `pass/conditional/reject` (conditional = within 0.12 below threshold). Below `--target-threshold` (default 0.7) the script **exits non-zero and refuses to patch the spec** unless `--allow-low-confidence`; the SKILL says treat low confidence "as a stop/refine-input signal, not as a pass". Explicit honesty field: `hardLimit: "A single image cannot uniquely recover true albedo/roughness/normal/AO"`.
  6. It also derives `surfaceFrequencyBands` amplitudes from measured value range/gradient stats and appends a `pbrExtractionHistory[]` audit trail to the spec.
- **Dual-track mapping**: adopt the *pattern* (numeric confidence + refusal to auto-patch below threshold + capped honesty for single references) even if we reimplement in Node/canvas. Realistic Three.js track: feed extracted palette + roughness base/variation into generated canvas textures. Blender-MCP track: same maps as image textures on Principled BSDF. Every material claim in design-spec.yaml carries `source: extracted|estimated` + confidence.

### 9. Look-dev triple screenshot (neutral / grazing / reference-match)

- **How it works exactly** [CERT-web]: material/lighting passes require three deliberate views before `continue` (`material-lighting-realism.md`): `neutral` (honest albedo/form), `grazing` (low-angle close-up "that exposes smooth-plastic highlights, weak normals, uniform roughness, and texture tiling"), `reference-match` (source camera+lighting). Rule: "A material that only looks convincing in the reference-matched light has not passed." Lighting pass requires named entries covering key light, fill, rim/environment, exposure/tone-mapping, and contact shadow — `lighting_pass_gaps()` greps `lightingFromPhoto[]` text for term groups (`key/sun/main`, `fill/ambient/hemisphere`, `rim/environment/hdr`, `exposure/tone/aces/filmic`, `contact shadow/ao`) and needs ≥3 concrete entries.
- **Dual-track mapping**: cheap and mechanical for Blender-MCP (script 3 camera/light setups). For the voxel→realistic Three.js loop, encode the 3 views as required review viewpoints in design-spec.yaml and ask the user for those 3 screenshots at material/lighting gates.

### 10. Comparison sheet as "evidence packaging, never the judge"

- **How it works exactly** [CERT-web]: `make_visual_comparison_sheet.py` only stitches reference+render side by side ("The sheet is only evidence packaging. It does not score the images."). Spec field `codePixelDiffIsAcceptanceAuthority: false`; scoring authority is AI vision inspecting one full pair, from which *both* the global score and all feature scores must come (`singleImagePairOnly: true`). Same-viewpoint rule: "do not judge a front reference against a random render angle."
- **Dual-track mapping**: our gate reviews should likewise ban pixel-diff/heuristic auto-acceptance; the multimodal model reads one composite image per gate (keeps token cost bounded — one image, N feature scores).

### 11. Calibrated fidelity ladder + honest failure vocabulary

- **How it works exactly** [CERT-web]: 0–1 fidelity anchors (`self-correction-loop.md`): 0.2 rough placeholder, 0.4 silhouette recognizable, 0.6 macro/meso correct + weak material, 0.75 reads correctly, 0.85 strong procedural match, 0.95 near-reference ("usually requires multiple views or manual art"); "Do not claim 0.9+ from a single ambiguous image." The skill explicitly legitimizes: "This cannot reach the requested fidelity from the current image. That is a valid self-correction result." Named resets from their prototype lessons: `Material Realism Reset`, `Silhouette Reset`, etc. — "Vague 'make it better' feedback is weak."
- **Dual-track mapping**: adopt the anchored scale for gate scores in design-spec.yaml so 0.75 means the same thing at every gate, and adopt named resets as the vocabulary of the client-satisfaction loop (matches our living-environment loop).

### 12. Image suitability gate before any work

- **How it works exactly** [CERT-web]: verdict `pass|conditional|reject` from seven 0–3 scores: `object_isolation, silhouette_readability, depth_inference, primitive_decomposition, material_procedurality, occlusion_risk, interaction_fit`; explicit reject list (ambiguous target, scene-not-object, demands exact mesh, subject dominated by hair/smoke/liquid/glass/lace) and an "ask for better input" list (front/side/back views, neutral background, close-ups, desired style) in `validation-rubric.md`.
- **Dual-track mapping**: becomes the intake gate of the 3D-design skill: when the client hands a reference photo of equipment/building, score it and either proceed, proceed-with-stated-assumptions, or request specific better inputs — before spec writing.
